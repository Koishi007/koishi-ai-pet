# 猜高低对赌游戏设计

> 桌宠与用户各自对「下一张牌比当前基准数字高还是低」下注；0-9 十张牌洗匀成牌堆，剩余牌公开，双方下注完成后揭晓，各分胜负。得分与所选边的真实剩余张数挂钩，先得 6 分者获胜。桌宠经 `game__play` 传 `hl_choice` 下注，用户在面板点击下注；抽牌在双方下注后发生，双方都无法预知结果。

## §0 背景与现状

游戏层现有四个回合制游戏：`guess_number`、`tic_tac_toe`、`rps`、`twenty_questions`（`pet/game/__init__.py:14-17` 的 `register_all` 注册）。每个游戏实现 `Game` 子类，经 `GAME` 容器承接工具调用，模型用 `game__init` 与 `game__play` 循环推进对局。

可复用的既有能力：

| 能力 | 现状 | 位置 |
|---|---|---|
| 游戏接口 | `Game` 基类：`name`/`description`/`new_state`/`args_schema`/`play` 与四类台词钩子 | `pet/game/gamebase.py:32-70` |
| 会话容器 | `GameBase`：`init`/`play`/`stop`/`forfeit`/`submit`，闲置清理 `SESSION_TTL = 120` | `pet/game/gamebase.py:73-403` |
| 跨线程提交 | `submit` 在 UI 线程写 `pending_move` 并 `wait_event.set()` 唤醒脑线程 | `pet/game/gamebase.py:94-111` |
| 等待用户 | 脑线程分段等待（0.2 秒步长），轮询 `_cancelled` 退出 | `pet/game/rps.py:180-196`、`pet/game/tic_tac_toe.py:259-285` |
| 面板推送 | `TOOL_CTX.game_board` 经 Qt 队列信号送主线程 | `pet/game/rps.py:198-212` |
| 面板基类 | 标题栏、倒计时、拖动、关闭即 `forfeit` | `pet/ui/game_panel.py:44-212` |
| 面板路由 | app 层按游戏名映射到 `render` | `pet/app.py:315-325` |
| 台词通道 | `win/lose/stop/forfeit_speech` 只在收尾事件出声；在途台词由模型的 aside/Speech 负责，`summary` 不播出 | `pet/game/gamebase.py:376-403` |
| 指令通道 | 给模型的推进指令走 `hint` 字段（`x-role: hint`），渲染在文本最后，不进历史 | `pet/tools/output.py` |
| 工具注册 | `game__list/init/play/stop` 元工具；`play` 参数由各游戏 `args_schema` 动态合并，统一降级为可选 | `pet/tools/registry.py:227-282`、`491-509` |
| 轮次预算 | 游戏工具不消耗 `LLM_TOOL_MAX_ROUNDS`，受独立上限 99 约束 | `pet/brain/behavior.py:481-487` |
| 看门狗豁免 | 有活跃对局时看门狗直接续命，等待用户不算挂死 | `pet/agent/scheduled_tasks.py:71-90` |

缺口有三处：现有游戏均为「桌宠出招、用户应对」或「用户藏答案、桌宠猜」的结构，没有双方各自下注、判定同时依赖双方选择的玩法；`play` 的返回值只有胜负与平局语义，没有分数竞赛的展示先例；面板没有牌堆与赔率一类策略信息的展示元素。

## §1 目标

- 桌宠与用户各自独立下注：双方押同一边时一起承担结果，押不同边时只有押中的一方得分、另一方扣 1 分。
- 抽牌在双方下注完成后进行，双方都拿不到下一张牌的信息。
- 剩余牌堆公开，得分与所选边的剩余张数挂钩（赔率制）。
- 先得 6 分者获胜；牌堆耗尽按比分结算；同分平局。
- 等待用户在面板点击期间阻塞脑线程，主线程 UI 不受影响，与猜拳、井字棋的等待模式一致。
- 超时、用户主动结束、外部取消三类语义与现有游戏一致。

## §2 非目标

- 不做跨局战绩持久化：最高分、连胜等记录留待后续。
- 不做音效与专属动作素材，揭晓反馈只用面板内样式与文案。
- 不做达成目标后继续加码的延伸模式。
- 不做用户出题、桌宠猜的角色互换。
- 不新增配置项：目标分、赔率封顶、超时秒数都是游戏模块常量。

## §3 牌堆与赔率

牌堆规则：

- `new_state` 时把 0-9 十张牌洗匀为 `deck`，翻开首张作基准 `base`，该张移出牌堆并进入 `history`。
- 点数两两不同，`base` 那张永远不在牌堆里：可用牌就是整个 `deck`，`above` 与 `below` 之和恒等于牌堆张数。
- 每轮揭晓从 `deck` 随机取一张并移出牌堆；揭晓数字成为下一轮的 `base`（无论双方是否命中）并进入 `history`。对赌模式下猜错不结束，基准统一按「揭晓即接续」推进。
- `deck` 抽空即牌堆耗尽，直接结算，不进入等待；首张作基准后剩 9 张，故单局最多 9 轮。
- 面板公开 `deck` 全量，已揭晓的牌不再出现在牌堆里。

赔率规则：

- 某边命中概率 `p = 该边张数 / (above + below)`；赔率 `s = ceil((above + below) / 该边张数)`，封顶 5。
- 张数为 0 的边不可选：用户侧按钮置灰；模型押中该边时返回错误并要求重押，不消耗轮次。
- 示例：

| above : below | 押「更高」 | 押「更低」 |
|---|---|---|
| 4 : 3 | 命中 4/7，得 2 分 | 命中 3/7，得 3 分 |
| 5 : 1 | 命中 5/6，得 2 分 | 命中 1/6，得 5 分 |
| 1 : 0 | 命中 1/1，得 1 分 | 不可选 |

## §4 回合时序

| 阶段 | 触发 | 行为 |
|---|---|---|
| 桌宠下注 | 模型调 `game__play` 并传 `hl_choice` | 校验枚举合法且该边有牌；失败返回错误提示重试，会话状态不变 |
| 展示 | `play` 内 | `TOOL_CTX.game_board` 推送 `waiting=True` 载荷：桌宠已下注（不泄露押哪边）、双方分数、牌堆、赔率 |
| 用户下注 | 面板点击「更高」或「更低」 | `GAME.submit` 写 `pending_move`，唤醒脑线程 |
| 揭晓 | `play` 被唤醒 | 抽牌，按 §5 判定双方，更新分数、`base`、`history`；载荷带 `pet_choice`，面板公开桌宠押哪边 |
| 继续 | 无人到 6 分且牌堆未尽 | 推送 `waiting=False` 结果载荷，返回 `ended=False`；模型出话后再次 `game__play` |
| 结束 | 有人到 6 分或牌堆耗尽 | 推送结果载荷，返回 `ended=True` 与 `won`；会话由容器清理，面板保留结果直至关闭或下一局开始 |

说明：

- 下注顺序固定：模型先下注（每次 `play` 只传自己的 `hl_choice`），用户后下注；用户下注前面板只显示「桌宠已下注」，揭晓后才公开桌宠押哪边。抽牌发生在用户点击之后，因此双方都无法预知下一张牌。
- 一次 `play` 推进一轮（一次揭晓）。模型在两次 `play` 之间说话，节奏与猜拳、井字棋一致。
- 超时：15 秒未点击结束本局，不算胜负（`timeout=True`，附收场台词）。与猜拳、井字棋的 `MOVE_TIMEOUT` 一致。
- 用户点面板 ×：`forfeit`，不算胜负。
- `game__stop` 或脑线程被替换：外部取消路径，`suppress_speech=True`，由调用方播收场词。

状态字段（`new_state`）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `deck` | list[int] | 剩余牌 |
| `base` | int | 当前基准 |
| `history` | list[int] | 已出现的数字 |
| `user_score` / `pet_score` | int | 双方分数 |
| `round` | int | 已揭晓轮数 |
| `wait_event` / `pending_move` / `move_lock` / `_cancelled` | - | 交互四件套，与其他游戏一致 |

## §5 判定与计分

判定表（`s_user` 与 `s_pet` 是各自所选边的赔率，双方押同一边时相同）：

| 双方下注 | 揭晓 | 用户分 | 桌宠分 |
|---|---|---|---|
| 押同一边 | 命中 | `+s` | `+s` |
| 押同一边 | 未中 | 不变 | 不变 |
| 押不同边 | 用户命中 | `+s_user` | `-1` |
| 押不同边 | 桌宠命中 | `-1` | `+s_pet` |

- 分数下限 0，单次得分封顶 5。
- 先得 6 分：`user_score >= 6` 判用户胜，`pet_score >= 6` 判桌宠胜；同一次揭晓双方同时到 6 分（只可能发生在双方押同一边且命中）判平局。
- 牌堆耗尽：比分高者胜，同分平局（`won=None`，与井字棋平局语义一致）。
- 判定与计分写成模块级纯函数，输入为基准、揭晓数字、双方下注与两边张数，输出双方分数变化与结果键，供单测直接调用。

## §6 面板与渲染载荷

面板布局自上而下：双方分数与目标（6 分）、「桌宠已下注」行、当前基准大字与历史链、剩余牌堆方块、两个下注按钮、结果文案。固定尺寸参照现有面板（约 360x400）。倒计时、拖动、关闭按钮由 `GamePanelBase` 提供。

载荷字段：

| 字段 | 类型 | 用途 |
|---|---|---|
| `base` | int | 当前基准 |
| `history` | list[int] | 已出现的数字链 |
| `deck` | list[int] | 剩余牌 |
| `above` / `below` | int | 两边张数 |
| `odds` | dict | `higher` 与 `lower` 各自的分值，值为 None 表示该边不可选 |
| `pet_choice` | str | 桌宠本轮下注 |
| `user_score` / `pet_score` / `target` | int | 计分区 |
| `revealed` | int 或 None | 本轮揭晓数字，结果载荷使用 |
| `outcome` | str 或 None | 结果键：押同一边命中、押同一边未中、押不同边用户命中、押不同边桌宠命中、耗尽、超时 |
| `waiting` / `message` / `timeout` | - | 基类约定字段 |

交互：下注按钮点击调用 `GAME.submit(game_name, {"choice": "higher" 或 "lower"})`，形态与二十问面板一致（`pet/ui/twenty_questions_panel.py:119-141`）。`waiting=False` 期间按钮禁用，点击不产生提交。

## §7 工具参数

| 参数 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `hl_choice` | str | `higher` / `lower`，前缀 `hl_` 全局唯一 | 桌宠本轮下注。每次 `game__play` 必传；缺失、非法或指向 0 张的边时返回错误并要求重押，不推进回合 |

参数描述要点：

- `hl_choice` 是桌宠的真实下注，用户下注前不可见，揭晓后公开。
- 抽牌发生在用户点击之后，桌宠无法预知结果，不在下注文案里暗示已知道结果。
- 返回值同时给出分数、牌堆分布与双方判定，模型据此调整下轮下注与台词。
- `play_args_schema` 把所有参数统一降级为可选（`pet/game/gamebase.py:137-158`），必填校验由 `play` 内部完成。

## §8 轮次预算与看门狗

游戏工具在元工具清单内（`pet/brain/behavior.py:481-487`），不消耗 `LLM_TOOL_MAX_ROUNDS`（默认 30，`pet/config.py:46`）配额；纯游戏流程只受元工具上限 99 约束（`pet/brain/tool_loop.py:82-88`）。

单局预算：

| 项 | 次数 |
|---|---|
| `game__init` | 1 |
| `game__play`（每轮下注 1 次，牌堆封顶 9 轮，6 分目标通常 3 到 8 轮分出胜负） | 3-9 |
| 无效下注重试 | 0-2 |
| 合计 | 6-12（上限 99） |

等待用户点击期间，看门狗检测到活跃对局即调用 `note_brain_progress` 续命（`pet/agent/scheduled_tasks.py:71-90`），不会按挂死回收脑线程。会话闲置清理（`SESSION_TTL = 120`）在正常交互节奏下不会触达：等待中的 15 秒超时会先把对局结束。

## §10 验证方式

自动化：

```bash
python -m pytest tests/test_higher_lower.py tests/test_game_registry.py
python -m pytest tests/test_docs.py
```

`tests/test_higher_lower.py` 覆盖：

- 牌堆：首张基准移出牌堆且不留在牌堆里、牌堆抽空即结算耗尽；
- 赔率：常规计算、张数 1 与封顶 5、某边 0 张返回不可选；
- 判定：四种组合的分数变化、下限 0、封顶 5；
- 结算：先得 6 分、同次揭晓同到 6 分平局、牌堆耗尽比分、同分平局；
- 参数：缺失与非法 `hl_choice`、押 0 张边被拒且状态不变；
- 等待路径：辅助线程调用 `play`，主线程经 `GAME.submit` 提交后断言返回值，并覆盖超时（缩短实例超时为小值）与取消（置 `_cancelled` 后提交）。

手动清单：

1. 开局后桌宠只显示「已下注」，押哪边不可见；用户下注并揭晓后显示「桌宠押：更高/更低」，下注按钮显示两边张数与分值；
2. 双方押同一边命中、押同一边未中、押不同边分出胜负三类结果的分数变化与文案；
3. 某边 0 张时按钮置灰；
4. 15 秒不点击，本局结束且不算胜负；
5. 面板 × 结束游戏，不算胜负；
6. 牌堆耗尽结算比分；先得 6 分结束；
7. 倒计时、面板位置、拖动与现有游戏一致。

## §11 风险与约束

- 判定依赖桌宠先下注：每次 `game__play` 必须先传 `hl_choice` 才进入等待，缺失即返回错误，不出现无桌宠立场的一轮。
- 同一次模型回复里连续多次 `game__play` 由工具层串行执行（`pet/brain/tool_loop.py:198-204` 的 `has_game_tool` 分支），不会乱序；连发会跳过中间的台词插入，不影响对局正确性。
- 模型押 0 张的边：返回错误并要求重押，`ended=False` 且会话保留，模型纠正后重试，与既有参数错误的处理路径同构（`pet/game/gamebase.py:204-216`）。
- 必然命中轮：某边 0 张时该轮只能押另一边并必然命中（1 分），属于设计内节奏，不额外处理。首轮 `base` 为 0 或 9 时即属此种。
- 等待竞态（框架级，既有行为）：`_wait_for_move` 先清 `pending_move` 再 `clear()` 事件，若提交恰好落在这两步之间，提交会被抹掉而 `submit` 仍返回 True，最终走到超时。猜拳与井字棋是同一写法，窗口为微秒级且需用户提前点击，实际概率趋近于零；根治要靠框架级轮次计数（epoch）统一处理三个游戏，另立任务。
- 台词：五组钩子只在收尾事件出声，按恋恋口吻写（短句、≤20 字、省略号）；在途台词由模型的 aside 负责，工具层不代写。
- 面板固定尺寸承载元素较多（分数、下注、数字、牌堆、按钮），实现时按约 360x400 排布，必要时裁减展示（如历史链只显示最近若干张）。
- 平局语义：`won=None` 时容器不上报胜负事件（`pet/game/gamebase.py:370-380` 只处理 True 与 False），与井字棋平局一致。

## §12 结论

改动面为两个新文件加三处登记：游戏实现与面板各自独立，判定与计分是纯函数可直接单测；等待、提交、超时、取消全部沿用现有游戏约定；轮次预算与看门狗由元工具机制覆盖，不需要框架层改动。
