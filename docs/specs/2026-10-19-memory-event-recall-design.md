# 事件记忆随机注入的时效处理设计

> event 类记忆按轮次逐条追加，同一件事的状态推进在库中是并列的多条记录；「你惦记着的事」随机抽一条注入，抽样不看后续更新，旧状态会与当前事实冲突。本设计以整点定时合并为主，读取侧取最新作为整点之间的兜底，注入文案补充时效提示。

## §0 现状

| 项 | 现状 | 位置 |
|---|---|---|
| 抽样 | `SELECT id, content, created_at FROM memories WHERE category = 'event' ORDER BY RANDOM() LIMIT ?` | `pet/brain/memory.py` 的 `random_events` |
| 排除 | 只排除上一轮注入过的 id，不排除同一主题 | `pet/brain/context_builder.py` 的 `_recent_event_ids` |
| 注入 | 随机结果写入「你惦记着的事」，前缀为「你忽然想起来的旧事，可以顺着说一句，不必特意去做什么」 | `_memory_event_note` |
| 条数 | `MEMORY_EVENT_RECALL_COUNT`，默认 1，0 关闭 | `pet/config.py` |
| 写入 | `Memory:` 行按 `category` 插入；`event` 类逐条追加 | `pet/brain/memory.py` 的 `save_from_line`、`save` |
| 既有合并 | 文本相似度 ≥0.85 走冷却拦截；中等相似按「取较长内容」合并 | `_do_merge` |

同一件事在库中的形态（示意）：

| 条目 | 内容要点 | 关键词 |
|---|---|---|
| 1 | 准备制作一段介绍视频，答应配合 | `[主题]`、`[配合]` |
| 2 | 某个镜头需重拍，等待指令 | `[主题]`、`[镜头]` |
| 3 | 该镜头仍待重拍 | `[主题]`、`[镜头]` |
| 4 | 视频已发布 | `[主题]`、`[发布]` |
| 5 | 该镜头已拍完，素材无需补拍 | `[镜头]`、`[完成]` |

条目 2、3 的状态已被条目 5 推翻，仍在抽样范围；条目 5 与条目 2 的关键词没有交集。

运行记录中出现过一种情形：抽到「某镜头需重拍」的条目后，模型输出了询问何时补拍的台词，而库中已有「该镜头已拍完」的条目。

判定相似度的实测分布（35 条 event 记忆，`LightweightDeduplicator.compute_similarity`）：

| 组 | 配对数 | 中位数 | 最大值 |
|---|---|---|---|
| 同一件事 | 75 | 0.194 | 0.529 |
| 不同事 | 156 | 0.051 | 0.154 |

同主题与不同主题在文本相似度上大幅重叠，该信号不能作为判定依据。关键词交集的表现相反：同一件事命中 30/75，不同事命中 0/156。

## §1 目标

- 注入的旧事反映事件当前状态，不出现已被后续记录推翻的内容。
- 合并产出是高质量事件记录，保留过程细节，不是压缩摘要。
- 合并覆盖全部 event 记忆，不按时间或抽样筛选；单次成本由 `MEMORY_MAX_CAPACITY` 约束。
- 表结构不变更。

## §2 非目标

- 不改「最近发生了什么」的运行时事件流（`note_event`）。
- 不改 `recall` 工具的检索与记忆面板的浏览。
- 不引入人工标注的事件分组。
- 不做增量合并：每次全量重算。
- 不在写入路径做同主题判定。
- 不保留被合并条目的原文：合并成功后旧条目删除。

## §3 定时合并

### §3.1 触发

- 使用 `Scheduler.schedule_at(timestamp_ms, callback, key)` 注册下一个整点（本地时间）的一次性回调，`key` 固定为 `memory_event_merge`，重复注册会覆盖旧闹钟。
- 回调开头先注册下一个整点，再执行合并；合并异常不中断链。
- 进程退出即停止，无后台守护；休眠唤醒或系统时钟调整后，按当前时间重新计算下一次整点。
- 触发时先判定是否执行：`SELECT MAX(created_at) FROM memories WHERE category='event'` 与上次合并时间比较，没有新增则跳过，不发起 LLM 调用。
- 回调由 QTimer 在主线程执行，LLM 调用与写回放到后台线程。
- 设置页提供「立即汇总」按钮：确认风险后执行一次，不检查整点间隔与 `MEMORY_EVENT_MERGE_ENABLED`，用于手动验证或临时收敛。

### §3.2 输入范围

```sql
SELECT id, created_at, content FROM memories
WHERE category = 'event'
ORDER BY created_at DESC
```

- 全时段覆盖：注入是随机召回，任何一条都可能被抽到，汇总必须覆盖全部 event 记忆，不按时间窗筛选。
- 条数由 `MEMORY_MAX_CAPACITY`（默认 200）约束，不设额外上限；容量清理会先行淘汰。
- 每次全量发送，不区分本小时新增与历史。同一批输入重算结果一致，无漂移。

### §3.3 输入协议

```
#1245 10-17 10:02 准备制作一段介绍视频，答应配合
#1248 10-17 10:59 某个镜头需重拍，等待指令
#1258 10-17 18:29 该镜头已拍完，素材无需补拍
```

- 每条一行：数据库 id、`MM-DD HH:MM`、原始内容。
- 用数据库 id 而不是序号：模型复制 id 比数序号可靠，解析端可直接回查输入集合。
- 日期省略年份，跨年时补 `YYYY-`；内容不截断，总量由 `MEMORY_MAX_CAPACITY` 控制。

### §3.4 提示词

四段结构，目的是把散落记录汇总成一条高质量事件记录，不是压缩成一句话：

```
[任务]
下面的事件记录中，哪些是同一件事的连续进展？只把这类记录汇总成组，其余记录不必处理。

[判断标准]
- 同一件事：围绕同一目标或对象的连续进展（准备、进行、完成、后续影响）
- 不同事：主题词相近但对象不同，不算同一件事
- 没有把握时不合并

[输出]
只输出需要汇总的组，每组一行：
Group: #编号,#编号 | 汇总内容
- 每组至少两条，没有可汇总的记录时留空
- 每条记录最多出现在一组
- 汇总内容写清最终状态，并保留过程中的关键细节：时间、对象、做过什么、结果如何
- 长度不超过 400 字，可读成一段连贯记录，不是关键词罗列
- 只输出 Group 行，不解释、不加代码块、不输出未分组的记录

[事件记录]
#1245 10-17 10:02 ...
```

| 项 | 约定 |
|---|---|
| 汇总定位 | 保留时间、对象、关键动作与结果，不缩写为电报体 |
| 长度上限 | 固定 400 字，超出截断 |
| 事实边界 | 只归纳输入中已有的内容，不新增、不推测 |
| 不合并的默认 | 没有把握时保持独立，漏合并下一轮仍可处理 |
| 输出范围 | 只输出需要合并的组，独立记录不出现 |
| 输出语法 | 只有 `Group:` 行，不给 JSON 等备选格式 |

### §3.5 输出协议与解析

```
Group: #1248,#1251,#1258 | 10-17 上午拍介绍视频，钓鱼镜头重拍后已补拍完成
Group: #1245,#1252 | 10-17 答应配合拍视频，当天已拍完
```

| 元素 | 约定 |
|---|---|
| 行首 | `Group:`，全角冒号同样接受 |
| id 列表 | `#` 前缀，逗号分隔，允许全角逗号与空格 |
| 分隔 | 第一个 `\|` 之前为 id 列表，之后为汇总内容 |
| 汇总内容 | 单行，不含换行 |

解析规则：

| 情形 | 处理 |
|---|---|
| 行首不是 `Group:` | 忽略该行 |
| id 不在输入集合 | 丢弃该 id，保留其余 |
| 去重后组内 <2 条 | 忽略整组 |
| 同一 id 出现在多组 | 只保留首组，其余组剔除该 id 后再判条数 |
| 汇总内容为空 | 忽略整组 |
| 汇总内容超长 | 截断到 400 字 |
| 没有任何有效组 | 本轮不写回 |
| 整行解析异常 | 记 warn 跳过，不影响其他行 |

预处理：全角转半角、剥离代码块标记、去除行首尾空白，与 `pet/brain/parsing.py` 现有的标签容错一致。

### §3.6 写回

- 每组插入一条新 event 记忆：`created_at` 取组内最大值，`keywords` 取组内并集，`importance` 取组内最大值；随后删除组内旧条目。
- 插入与删除在同一事务内，任一步失败整体回滚。
- 合并产物的 `created_at` 与原始事件保持同一时间基准，注入时的时间提示不因合并而重置。
- 删除前在日志记录被删条目的 id 与内容前 50 字，供排查误合并。
- 未出现在任何 `Group` 行中的条目保持独立，不做删除。不得按「输入总数减去已合并数」反推待删条目。

### §3.7 模型连接

| 键 | 默认 | 说明 |
|---|---|---|
| `MEMORY_MERGE_URL` | 空 | 合并请求的 API 地址，三项齐全才生效 |
| `MEMORY_MERGE_KEY` | 空 | 合并请求的 API Key，三项齐全才生效 |
| `MEMORY_MERGE_MODEL` | 空 | 合并请求的模型名，三项齐全才生效 |

- 位置：设置「行为」页签的记忆章节，三项均可选。
- 生效条件：三项全部填写时使用独立连接；任意一项为空时整组不生效，URL、Key、模型全部沿用「当前启用的模型方案」（`LLM_ACTIVE_PROFILE` 指向首选或备选）。
- 请求参数：温度固定 0.2、思考开启、非流式、超时沿用 `LLM_TIMEOUT`；解析失败不在本轮重试，等下一个整点。
- 输出预算固定 8192，思考与正文共用（实测思考约 2.4k、正文约 0.3k）；不读取用户可见的输出 Token 配置（该配置已收归代码，见 `docs/decisions/0010-output-budget-in-code.md`）。

## §4 兜底 A：读取侧取同主题最新

- 落点：`MemoryStore.random_events`。
- 流程：随机取一条种子，按关键词交集取候补，返回候补中 `created_at` 最大的一条；未命中返回种子。
- 判定只用关键词交集（非空），不使用文本相似度（依据见 §0 的分布）。
- 候补不限时间，与合并范围一致；同主题候补取 `created_at` 最大的一条。
- 作用范围：整点合并之间新写入的条目。

## §5 时效提示 D

- 落点：`_memory_event_note` 的前缀与条目后缀。
- 前缀取「（旧事，之后可能有变化；合适时顺口提一句即可，不必当成现状）」。
- 每条末尾追加 `（3 天前）` 形式的时间，由 `format_memory_time` 生成，与记忆面板一致。

## §6 组合与优先级

| 层 | 时机 | 判定依据 | 作用 |
|---|---|---|---|
| 定时合并 | 整点 | LLM | 主：生成事件汇总，删除同主题旧条目 |
| A | 每轮注入 | 关键词交集 | 整点之间的兜底 |
| D | 每轮注入 | 无 | 时间提示，避免旧事被当成现状 |

|---|---|---|---|---|
| `MEMORY_EVENT_RECALL_COUNT` | int | 1 | 显示 | 每轮注入条数，0 关闭 |
| `MEMORY_EVENT_MERGE_ENABLED` | bool | false | 显示 | 整点定时合并开关 |
| `MEMORY_MERGE_URL` | str | 空 | 显示 | 合并请求的 API 地址，三项齐全才生效 |
| `MEMORY_MERGE_KEY` | str | 空 | 显示 | 合并请求的 API Key，三项齐全才生效 |

## §8 验证

| 用例 | 断言 |
|---|---|
| 整点注册 | 注册后闹钟指向下一个整点；重复注册覆盖旧闹钟 |
| 无新增跳过 | `MAX(created_at)` 不晚于上次合并时间时不发起调用 |
| 输入范围 | 包含全部 event 条目，按时间倒序 |
| 输入格式 | 每行为 id、`MM-DD HH:MM`、内容三段 |
| 解析：全角符号 | 全角冒号与全角逗号可解析 |
| 解析：代码块包装 | 带代码块标记的输出可解析 |
| 解析：跨组重复 id | 重复 id 只保留首组，其余组剔除后按条数判定 |
| 解析：非法输出 | 全无有效组时不写回 |
| 写回 | 每组生成新条目、删除组内旧条目；`created_at` 取组内最大值 |
| 事务回滚 | 写回中途异常时新条目与删除操作均不生效 |
| 未提及条目 | 未出现在任何 `Group` 行中的条目不删除 |
| 模型连接生效 | 三项齐全时使用独立连接；缺任意一项时整组不生效，全部沿用当前启用方案 |
| 汇总长度 | 超过 400 字时截断 |
| A 取最新 | 种子为旧状态条目时，返回同主题最新条目 |
| A 无交集 | 候补关键词无交集时返回种子 |

手工核对：

```sql
SELECT id, created_at, content FROM memories
WHERE category = 'event' ORDER BY id;
```

## §9 风险

| 项 | 影响 | 处理 |
|---|---|---|
| 误合并不可恢复 | 不同事件被合成一条，原文已删除 | `MEMORY_EVENT_MERGE_ENABLED` 默认关闭；日志记录被删 id 与内容前 50 字；组内 ≥2 条，汇总须覆盖组内状态 |
| 汇总过长 | 注入时占用上下文 | 单组固定上限 400 字；总量由容量上限控制 |
| 整点前矛盾暴露 | 新状态写入后到下一次整点之间，旧条目仍可能被抽到 | A 按关键词收敛；无交集时由 D 的文案限定为旧事 |
| 整点错过 | 休眠或卡顿后不补 | 下一次整点按当前时间重算，最多延迟一小时；期间由 A 兜底 |
| 输入量随事件总量增长 | 单次 token 上升 | 由 `MEMORY_MAX_CAPACITY` 约束上界（默认 200 条） |

## §10 记忆面板按类别筛选

### §10.1 现状

| 项 | 现状 | 位置 |
|---|---|---|
| 筛选栏 | 级别、重要性、日期范围、关键词 | `pet/ui/memory_window.py` 的 `_build_filter_bar` |
| 查询 | `list_memories(level, importance, search, start_date, end_date, page, page_size)` | `pet/brain/memory.py` |
| 类别 | 只在详情面板以文本显示，不参与筛选 | `_detail_category` |

### §10.2 改动

- `list_memories` 增加 `category: str = ""` 参数，非空时在 `where` 追加 `AND category = ?`。
- 类别在 `pet/brain/memory.py` 以常量 `MEMORY_CATEGORIES` 定义；提示词 `_MEMORY_GUIDE` 的类别定义与此保持一致。
- 筛选栏第一行增加类别下拉，选项为「全部」加 `MEMORY_CATEGORIES`；切换后回到第 1 页并刷新列表。
- 类别不按库中出现的值动态生成：空库时没有选项，模型越界写入的类别也不应成为筛选项。
- 合并与筛选的关系：整点合并只删除 `event` 类条目，按类别筛选可直接核对剩余 event 条目与汇总内容。

### §10.3 验证

| 用例 | 断言 |
|---|---|
| 单选类别 | 选中 `event` 时只返回 `category = 'event'` 的行 |
| 组合筛选 | 类别、级别、日期、关键词同时生效，条件之间为与关系 |
| 分页 | 切换类别后回到第 1 页，总数随类别变化 |
| 选项来源 | 下拉为「全部」加 `MEMORY_CATEGORIES`，顺序固定，与库内容无关 |
