# 0010 输出上限收归代码并按请求形态配额

- 状态：已采纳
- 相关代码：`pet/brain/budget.py`、`pet/brain/behavior.py`（`_thinking_for_repair`、`_note_budget_truncation`）、`pet/brain/parsing.py`（`note_finish_reason`）
- 相关文档：[specs/2026-10-16-output-budget-design.md](../specs/2026-10-16-output-budget-design.md)

## 背景

- 输出上限原有五个键（交互 / 聊天 / 自主可见，分析 / 摘要隐藏），界面范围 100~8000。用户既不知道 `max_tokens` 的语义，也不知道该填多少，改小会直接破坏表现。
- `max_tokens` 是单次 completion 总量且含思考，同一个数值还复制给工具循环的每一轮。思考占满额度时流以 `finish_reason=length` 结束，整段输出作废；随后的空响应修复再用同预算、同思考设定重跑一次，额度落空两次。
- 该数值不影响成本（服务商按实际生成量计费），只决定输出能否完整落下，因此上调的代价仅限于放任失控生成。

## 决定

- 删除全部输出上限配置键，预算改由 `pet/brain/budget.py` 计算：基线（按模式）+ 思考预留（开思考时）+ 工具预留（首轮带 tools 时），统一硬上限 8192 封顶，数值不对外开放。
- 思考状态的判定与请求参数注入同源（`thinking_active`），避免预算与请求参数在「本次是否带思考」上出现分歧。
- 空响应修复只在上一轮 `finish_reason=length` 时关闭思考，其余失败保持调用方与用户设定。
- `finish_reason` 由解析器经 sink 回传编排方，日志把「预算耗尽」与「格式类失败」分开。
- 另一条路：保留一个高级上限键供小显存或本地模型使用。否决理由是它把同一个语义再暴露一次，而这正是本次要消除的问题；服务商侧的限制改由设计文档 §8 的降级路径处理。

## 后果

- 用户失去按模式调额度的入口；旧 `settings.json` 里的残留键被 `Config._load_user_settings` 过滤，不报错也不生效。
- 收益：开思考与带工具的请求上限被抬高，思考不再直接从正文基线的额度里扣；交互类小请求不需要与决策档同级的额度。
- 代价一：硬上限是常量，服务商拒绝较大的 `max_tokens` 时没有自动降档，当前会退回本地兜底；补降级的位置与做法见设计文档 §8。
- 代价二：配额数值取自当前模型的运行结果，换更重的思考模型后需按设计文档 §8 的方法复测。
- 未做：工具轮的最终输出仍带动作兜底（`pet/brain/tool_loop.py`），该路径上的截断不可辨识，记在设计文档 §8。
