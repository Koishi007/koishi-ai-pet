# 0016 语音输出用波形合成而非 TTS

- 状态：已采纳
- 相关代码：`pet/voice/phoneme.py`、`pet/voice/animalese.py`、`pet/ui/audio/audio_out.py`、
  `pet/ui/audio/vocalizer.py`、`pet/ui/speech_bubble.py`
- 相关文档：[语音输出设计](../specs/2026-11-27-vocalization-design.md)

## 背景

台词只以气泡文字出现，桌宠在窗口切到后台时不可感知。可选的三条路线代价差异很大：
云端 TTS 会把每条台词送出本机并按量计费；本地 TTS 要下发语音模型与推理栈，体积与内存
远超现有全部依赖之和；波形合成不需要模型也不需要素材。

同时，音频设备会话的建立实测耗时约 950~1040 ms 并同步阻塞调用线程，`sounddevice` 同量级，
换库没有收益。这一条决定了播放通道不能每句新建。

## 决定

- 用波形合成替代语音模型。单个音节是基频与两条谐波的叠加乘指数衰减包络，采样率 22.05 kHz、
  单声道、int16。产物是「像说话的声音」而不是「说出内容的语音」，可懂度不是目标。
- 音高由字符本身决定，取码点哈希而非随机数，同一个字每次音发同一个音高。音区由四档预设
  `deep` / `soft` / `bright` / `clear` 给出，用户可选，默认 `soft`。
- 播放通道常驻一个 `QAudioSink`：`start()` 只做一次，空闲 `suspend()` 使 CPU 归零，
  发声前先喂数据再 `resume()`。不用「保持 active 喂静音」，那会恒定消耗约 2.5% CPU。
- `QAudioSink` 只在工作线程创建，调用方与界面不承担初始化阻塞。`readData` 与 `feed` 同在
  该线程，队列因此不加锁，跨线程喂入经信号投递。
- 逐字发声而不是整句播放：打字机本来就逐字显示，逐字发声与视觉同步，且流式台词在收齐前
  无法整句合成。音节时长由打字间隔派生并夹在 30~60 ms，避免播放队列持续积压。
- 台词被作废时同步清空音节队列：修复轮会丢弃半截台词，声音不能继续播。

## 后果

- 收益：零新增依赖、零语音素材、零磁盘占用。`QtMultimedia` 随已有的 `PySide6_Addons` 就在依赖里。
- 收益：开关关闭时不创建线程、不打开设备，行为与没有该功能时一致。
- 收益：合成器与播放通道各自可替换；换成分片拼接只需改 `animalese.render`，调用方不动。
- 代价：首次发声前约 1 秒静默，这是设备会话建立的代价，只能选择在哪一刻付。
- 代价：部署体积增加约 19 MB，来自 QtMultimedia 与 FFmpeg 库。
- 代价：挂起对独占模式的声卡不友好，用户用独占 WASAPI 或 ASIO 播放音乐时可能互相影响。
- 约束：`QAudioSink` 在非主线程的行为只在 Windows 实测过，macOS 与 Linux 落地时需要各跑一次冒烟。
- 约束：`phoneme.py` 与 `animalese.py` 只能依赖标准库与 numpy，不得在顶层 import Qt，由 `ARCH005` 守住。
  播放通道因必须继承 Qt 类而放在 `pet/ui/`，那里本就放行顶层 Qt 导入，不需要 allowlist 条目。
